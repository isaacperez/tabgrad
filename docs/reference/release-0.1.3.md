# Tabgrad 0.1.3 source and support record

This record identifies ordinary `@tabgrad/tabgrad@0.1.3`, selected npm channel
`latest` and repository tag `v0.1.3`, under the [release policy](../releases.md).
Source metadata is separate from registry availability and operational delivery:
the release evidence identifies the source revision, exact archive/inventory,
original producer proofs and observed publication outcome.

## Maintainer corrections

[Release output names](https://github.com/isaacperez/tabgrad/issues/398) accept
the digits in their own SHA-256 fields, while rejecting malformed names and
multiline values. Both preparation and protected-role handoffs use their actual
Actions output sinks.

[Registry observation and diagnostics](https://github.com/isaacperez/tabgrad/pull/382)
bound post-publication propagation waiting and retain safe consumer failure
information. [Browser selection](https://github.com/isaacperez/tabgrad/pull/386)
uses the actual qualifier interface. These corrections preserve uncertainty and
do not retry an unknown publication.

[Stable-profile admission](https://github.com/isaacperez/tabgrad/pull/394) and
[CI preparation](https://github.com/isaacperez/tabgrad/pull/395) derive the exact
publication plan from reviewed version/source, original producer artifacts,
source checks, complete history and attributed physical GPU evidence. Protected
approval remains separate from generated data. The
[publication procedure](release-publication.md) owns commands, independent
trust enrollment, remaining manual approvals and failure recovery. Source
integration does not establish effective settings or a completed live delivery.

[Retained history transfer](https://github.com/isaacperez/tabgrad/pull/384)
avoids another upload of unchanged originals. Contributor validation and agent
handoffs select affected checks and reuse applicable evidence
([CI](https://github.com/isaacperez/tabgrad/pull/388),
[workflow](https://github.com/isaacperez/tabgrad/pull/390)). These are maintainer
changes, with no tensor API or performance expansion.

## Preserved support and qualification

The [0.1.2 support record](release-0.1.2.md), including its inherited API-group
and numerical boundaries, applies unchanged. PyTorch support remains
**Partially supported**: the same calls, values, errors, warnings, identities,
aliases, gradients, partial progress, float32/layout/device limits and declared
environments. Runtime, Python, kernels, conformance data and dependency
resolution are unchanged. Release-tool corrections are not additional hardware
coverage, universal compatibility or speed/memory guarantees.

Changed version metadata and packaged guidance require their own exact
candidate. The controlled main producer qualifies and signs its retained bytes;
physical supplied-archive and installed-registry qualification remain distinct.
Actual reports identify browser/device, archive/inventory and cleanup limits.
Source checks, earlier signatures or controlled test reports cannot substitute
for those observations. Applicable immutable evidence retains its original
source and scope when reused.

## Maintenance and updating

When admitted as the latest ordinary release, `0.1.3` supersedes `0.1.2` under
the existing default-branch maintenance policy. Historical records are retained;
no backport branch, LTS promise or new grace period is introduced.

Applications need no tensor API migration. Install the exact verified version
and replace the complete matching static asset tree under the
[installation and ownership contract](browser-package.md). Maintainers moving
to version/source preparation separately enroll the stable trust profile; the
explicit closed-plan recovery path remains available under its own admission.
